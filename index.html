v0.1 — an agent in 18 linesv0.1/

No classes, no framework ceremony. A plain function becomes a tool; create_agent() wires the loop.

v0.1/agent-v0.1.py

from langchain.agents import create_agent
from langchain_aws import ChatBedrockConverse

def get_weather(city: str) -> str:
    """Get weather for a given city."""
    return f"It's always sunny in {city}!"

model = ChatBedrockConverse(
    model="us.anthropic.claude-opus-5",
    region_name="us-east-1",  # pinned
)

agent = create_agent(model=model, tools=[get_weather])

result = agent.invoke({"messages": [
    {"role": "user", "content": "What's the weather in Mumbai?"}
]})
print(result["messages"][-1].text)

What the model actually sees

  • function name → tool name
  • docstring → tool description (how Claude decides when to call it)
  • type hints → JSON Schema {"city": "string"}
  • the body never leaves your machine — the model only asks, your process executes

One invoke() = two HTTPS calls

  • ① request + tool schema → ② stopReason: tool_use
  • ③ your code runs the tool locally
  • ④ full history resent (API is stateless) → ⑤ end_turn

v0.3 — memoryv0.3/

One new line — a checkpointer — and the agent holds a conversation. thread_id picks which conversation.

v0.3/agent-v0.3.py — the diff that matters

from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(model=model, tools=[get_weather],
                     checkpointer=InMemorySaver())

agent.invoke({"messages": [...]},
             {"configurable": {"thread_id": "chetan"}})

Every turn: load the thread's history → run the loop → save it back.

Live transcript (real run)

you [demo]>  Hi! My name is Chetan and I live in Mumbai.
agent> Good news — it's always sunny in Mumbai! 🌞
you [demo]>  What's my name?
agent> Your name is Chetan, and you live in Mumbai ☀️
you> /thread other        # fresh conversation
you [other]> What's my name?
agent> I don't have any way to know your name…

Same process, two threads — memory is per-thread_id. And the wire is still stateless: the checkpointer replays history; the model remembers nothing.

v0.4 — real toolsv0.4/

The fake weather stub becomes a live API call, and an MCP server contributes 14 tools we never wrote. The model can't tell the difference — a tool is just a name, description and schema.

v0.4/agent-v0.4.py — the diff that matters

# get_weather now calls Open-Meteo (real data, no API key)
geo = requests.get(GEOCODE_URL, params={"name": city})
wx  = requests.get(FORECAST_URL, params={...})

# + 14 tools from the official filesystem MCP server
MCP_SERVERS = {"filesystem": {
    "transport": "stdio", "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-filesystem", REPO],
}}
mcp_tools = await MultiServerMCPClient(MCP_SERVERS).get_tools()
agent = create_agent(model, tools=[get_weather, *mcp_tools])

MCP tools are async, so invoke → ainvoke. The loop itself is unchanged.

v0.5 — deployed on AgentCorev0.5/

The agent didn't change — its home did. The REPL becomes an HTTP entrypoint, agentcore deploy ships it to Amazon Bedrock AgentCore Runtime, and every conversation gets its own isolated microVM.

v0.5/WeatherAgent — the diff that matters

app = BedrockAgentCoreApp()

@app.entrypoint
async def invoke(payload, context):
    # same loop, same get_weather tool
    session_id = context.session_id  # = thread_id (v0.3!)
    result = await graph.ainvoke(...)
    return {"result": result["messages"][-1].text}
agentcore create   # scaffold (LangChain/LangGraph template)
agentcore dev      # local chat UI on :8081
agentcore deploy   # CDK: IAM + runtime, CodeZip — no Docker
agentcore invoke "What's the weather in Mumbai?"

Same memory trick as v0.3 — the runtime's session_id becomes the thread_id. Each session runs in its own microVM, so InMemorySaver just works, isolated per user. Durable, cross-session memory? That's AgentCore Memory — v0.6.

v0.6 — durable memoryv0.6/

InMemorySaver retires. AgentCore Memory is a managed service: short-term checkpoints persist per session, and the service extracts facts & preferences in the background — so a brand-new session already knows you. A fresh project, its own stack: WeatherAgentV6.

v0.6/WeatherAgentV6 — the diff that matters

# scaffolded with memory from birth:
agentcore create --name WeatherAgentV6 --memory longAndShortTerm

# in main.py — InMemorySaver is gone:
checkpointer = AgentCoreMemorySaver(MEMORY_ID)      # short-term
store = AgentCoreMemoryStore(memory_id=MEMORY_ID)   # long-term

graph = create_react_agent(model, tools=tools,
    checkpointer=checkpointer, store=store,
    pre_model_hook=pre_model_hook)  # save msgs + inject recalls

Four strategies: SEMANTIC facts, USER_PREFERENCE, SUMMARIZATION, EPISODIC. Extraction runs asynchronously ~30s after each turn.

Proof — two separate cloud sessions

  Mumbai, and I prefer short answers."
agent> Hi Chetan! Noted — Mumbai, short answers.
Session: e1a6be71-…

# ~1 minute later — a BRAND NEW session:
$ agentcore invoke "What do you know about me?
  And what's the weather where I live?"

       (87%), light wind.

It knew the city and honored "short answers" — the terse reply is the preference memory working. Extracted memories, verbatim: "The user's name is Chetan · lives in Mumbai · prefers short answers."

v0.7 — the gatewayv0.7/

The tool leaves the codebase. Open-Meteo's endpoints become gateway targets — one from an OpenAPI spec, one from a 15-line Lambda — and the agent discovers them as MCP tools. Credentials are injected at the edge; the agent process never sees a key. Fresh project, own stack: WeatherAgentV7.

v0.7/WeatherAgentV7 — the diff that matters

# tools are now project config, not code:
agentcore add gateway --name WeatherGateway
agentcore add credential --name OpenMeteoKey --api-key …
agentcore add gateway-target --type open-api-schema \
  --name GeoAPI --schema specs/open-meteo-geocoding.json
agentcore add gateway-target --type lambda-function-arn \
  --name ForecastTool --lambda-arn arn:…:WeatherAgentV7Forecast

# in main.py, the ONLY tool wiring left:
client = MultiServerMCPClient({"gateway": {"transport":
  "streamable_http", "url": GATEWAY_URL}})
tools = await client.get_tools()
# -> ['GeoAPI___geocodeCity', 'ForecastTool___getCurrentWeather']

Proof — live from the cloud

$ agentcore invoke "What's the weather in Mumbai right now?"
# gateway chain: geocodeCity → getCurrentWeather

       humidity 84%, wind 14 km/h.

Memory from v0.6 carries over — a brand-new session still knew Mumbai and kept the answer short. The agent code contains zero weather logic; both tools come from the gateway.

1 · Models don't execute

The model only names a tool + arguments. Your process runs it.

2 · The API is stateless

The whole conversation is resent on every single call.

3 · The loop is the agent

model ⇄ tools until no more tool calls. Everything else is plumbing.
